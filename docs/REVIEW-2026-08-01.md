# KubeJob 深度 Review（设计 + 代码）

> 审查时间：2026-08-01
> 方法：通读设计文档（architecture / logical-architecture / message-transport / security / hardening-review / 14 篇 ADR）+ 5 路并行模块代码走查（Core / ControlPlane+PostgreSQL / Worker / Transport+Server / Client+Generator+Tests）+ 对每条高风险 🔴 结论逐行核对源码。
> 范围：当前工作树（src/ 134 个 .cs + docs/）实际实现，对照设计契约与 5 条正确性不变量。

---

## 0. 一句话结论

**设计成熟度很高**——ADR 驱动、契约先于实现、零信任、fencing/lease 精确到 Attempt 级、幂等/重复投递/乱序都有明确不变式。
**实现整体扎实**，但发现 **2 个会导致生产故障的确证 🔴 缺陷**（均在 PostgreSQL 存储层）、**若干 🟡 风险**（安全默认 fail-open、迁移可重入性、BrokerDispatch 默认档的对象解析待验证），以及一批🟢 细节。
我用逐行核对修正了 5 处子代理的"假阳性"（见第 4 节），避免误报误导。

## 1. 设计 Review

### 1.1 设计层面的亮点（值得肯定）
- **契约先行**：`Runtime/` 下协议类把"1 个幂等键→至多 1 个 Run"、"1 个 Run→至多 1 个当前 Attempt"、"只有未过期 lease 能改 Attempt"、"调度游标推进 + 出现 Run 必须在同一事务"五条不变量写成显式类型与注释。
- **零信任边界清晰**：transport（RabbitMQ）只承载 `queue + runId + eventId`，绝不带 lease/fencing；HTTP API 与 Dashboard 都声明"永不外泄 LeaseToken/FencingToken"。
- **双执行模型（Pull + BrokerDispatch）统一抽象**：`ExecutionDispatchProtocol`/`ExecutionAdmissionProtocol`/`JobIngressProtocol` 三层协议让两种交付档在 Worker 侧收敛到同一 `WorkerControlPlane` 接口，认知负担低。
- **安全回顾文档（hardening-review.md）质量高**：逐条列出已缓解威胁 + 残余风险 + 缓解建议，并诚实标注"fail-open 是历史兼容取舍"。

### 1.2 设计风险（🟡，需决策/澄清）

- **🟡 安全默认 fail-open（部署级最高风险）**
  `KubeJobServerExtensions.cs:205-220` 的 `KubeJobApiAuthorizationConvention` 仅在配置了 `_clientPolicy`/`_workerPolicy` 时才挂 `AuthorizeFilter`；`KubeJobServerExtensions.cs:263-269` 注释明确"authorization remains opt-in for backward compatibility"。即**未配置策略时，提交/Worker 控制/Dashboard 全部匿名可访问**。
  设计文档已说明这是 opt-in，但若某次部署漏配策略即裸奔。建议改为 **fail-closed**：默认拒绝，显式 `AllowAnonymous` 才开放健康检查等少数端点；至少把"未配置策略"从 warning 升级为启动失败或拒绝监听 0.0.0.0。

- **🟡 BrokerDispatch 成为默认投递档后，Schedule 路径的 TransportId 解析需确认**
  ADR 014 将默认投递档提升为 `BrokerDispatch`，`JobScheduleRuntimeModels.cs:34` 的 `JobScheduleRecord.DeliveryProfile = BrokerDispatch`，而 `UpsertCronScheduleRequest`（`JobScheduleProtocol.cs`）**没有 TransportId 字段**。同时 `DeliveryTarget.Validate`（`JobRuntimeProtocol.cs`）要求 `profile == BrokerDispatch ⇒ TransportId 必填`。
  需确认：控制面在提交 Schedule 触发的 Run 时，是否从 `QueueDeliveryOptions.DefaultTransportId`（ADR 014 默认 `"rabbitmq"`）回填 TransportId。若未回填，`DeliveryTarget.Validate` 会在调度触发路径抛错。建议要么在协议层允许"未指定则按 DefaultTransportId 解析"，要么显式回填并加单测覆盖。

- **🟡 能力→字段/API 映射文档分散，易被误读**
  `JobEnqueueOptions` 的边界（Queue/IdempotencyKey/MaxAttempts/Timeout/ConcurrencyKey/RetryPolicy/Continuation/Compensation/DeliveryProfile/Batching/Sharding）与 `Schedule`（独立 `IJobScheduleClient`）、`Placement`（队列路由）、`Broadcast`/`Sharding`（`docs/adr/011` 明确"部署拓扑而非逐作业字段"）在文档中分散在多篇。建议在 `job-enqueue-options.md` 或 README 补一张"能力 → 哪个 API/哪个字段"对照表，避免实现者与使用者误以为某些能力应出现在 `JobEnqueueOptions` 上。

- **🟡 客户端缺显式 API 版本协商**
  `message-transport.md` 提到"消息版本化由协议头承载"，但 HTTP 客户端（`HttpJobClient`/`HttpJobScheduleClient`）未强制协商/校验服务端版本。建议在客户端请求头带 `X-KubeJob-Client-Version` 并对不兼容响应做显式失败，而非静默 404 兜底。

### 1.3 设计与实现的整体一致性
| 设计契约 | 实现核对 | 结论 |
|---|---|---|
| 幂等键唯一 | `UQ_Kj2_JobRuns_Idempotency` + 事务内 dedup | ✅ 一致 |
| lease 隔离 `FOR UPDATE SKIP LOCKED` | Claim/Completion 事务核对 | ✅ 一致 |
| Worker fencing 触发 = heartbeat 被拒 | `FenceSession()`（`WorkerRuntimeService.cs:734-742`） | ✅ 一致 |
| BrokerDispatch ACK-after-complete | transport 注释与 worker 路径 | ⚠️ 见第 3.4 节待核对 |
| 调度游标 + 出现 Run 同事务 | `CommitScheduleFire` | ⚠️ 见 1.2（TransportId） |

## 2. 代码 Review（按模块）

### 2.1 KubeJob.Storage.PostgreSQL —— **确证 🔴**

**🔴 Bug A：`SubmitBatchAsync` 丢失 Continuation/Compensation 数据（数据丢失）**
`src/KubeJob.Storage.PostgreSQL/Runtime/PostgreSqlJobRuntimeStore.Submission.cs:193-223`
批量插入的列清单为 `Id,Queue,JobKey,PayloadJson,IdempotencyKey,MaxAttempts,TimeoutSeconds,Priority,AvailableAt,ConcurrencyKey,OrderingSequence,RetryPolicyJson,MetadataJson,Version,CreatedAt,Phase,Status,ScheduleId,ScheduledFor,DeliveryProfile`（`unnest` 与 `SELECT item.*` 同步缺列），**没有 `ContinuationJson` / `CompensationJson`**。而单条 `SubmitAsync`（同文件 :57）是包含的。
影响：任何通过 `EnqueueBatchAsync` 提交且带 `Continuation`/`Compensation` 的作业，在持久化后这两段 JSON 为 NULL → 补偿/续跑语义静默失效。
修复：在批量 INSERT 列清单与 `unnest`/`SELECT item.*` 投影中补 `ContinuationJson, CompensationJson`（与单条路径对齐）。

**🔴 Bug B：`GetByIdempotencyKeyAsync` 查错表名（运行期必抛错）**
`src/KubeJob.Storage.PostgreSQL/Runtime/PostgreSqlJobRuntimeStore.Submission.cs:500` 写的是 `FROM kubejob.Runs`，但迁移创建的真实表是 `Kj2_JobRuns`（`DbInitializer.cs:43`），且同文件其余 9 处查询（:23/:57/:99/:194/:264/:335/:354/:398/:424）全部用 `Kj2_JobRuns`。
影响：所有"按幂等键查 Run"的调用（含 `JobControlPlane.GetRunByKey`/`TryGetRunByKey` 等）会在 PostgreSQL 抛出 `relation "kubejob.Runs" does not exist`。
修复：改为 `FROM Kj2_JobRuns`。

**🟡 风险（待确认/非阻断）**
- `DbInitializer.cs` 的 v4 迁移：`CREATE TABLE IF NOT EXISTS` 幂等，但 `:283-397` 的 `ALTER TABLE` 步骤若未按事务包裹、`ADD COLUMN` 未用 `IF NOT EXISTS`，重跑迁移会失败。建议将整段迁移包进单事务并全部用 `IF NOT EXISTS`/幂等写法。
- `ReconcileSchedulesAsync` 用 schema 限定 `Kj2_JobSchedules`，其余方法不限定——风格不一致（非缺陷，但建议统一）。
- LeaseReaper 的 2s 作业认领窗口（`docs/adr/011`）：短超时作业在极端负载下可能被 reaper 误判 LeaseLost 而双重执行；lease 过期是正确性兜底，但建议把"作业认领窗口"与"lease 时长"解耦配置。

### 2.2 KubeJob.Core

**🟢 亮点**：`RetryPolicy`（Exponential 用 `Math.Max(0, attemptCount - 1)` 做指数底数、Jitter 用 `Random.Shared` 并夹在 `[0, delay]`）、协议类注释、泛型 `JobKey<T>` 不可变设计、`JobExecutionContext` 只读封装（仅持有 `JobRunRecord`/`ServiceProvider`/`Lease`/`Fencing`，不泄露 token 原始字符串）都写得很稳。

**🟡 风险**
- `JobIngressResult` 的 `bool Existing`（`JobIngressProtocol.cs:85-96` + `Execution/Ingestion.cs:94`）无法区分"**幂等键冲突**（不同 payload、同 key）"与"**重复投递**（同 message id）"。当前 `Existing=true` 两者都返回，调用方无法识别真正的冲突以告警。建议增加 `IngestionOutcome` 枚举（`Created` / `DuplicateDelivery` / `IdempotencyConflict`）。
- `RetryPolicy.Linear`（`RetryPolicy.cs:62-67`）定义为 `BaseDelay * attemptCount`，与 Exponential 基线不同属**设计如此**（已逐行核对，非 off-by-one bug）。唯一可加的健壮性是 `Math.Max(0, attemptCount)`，但 `attemptCount>=1` 恒成立，低优先。

### 2.3 KubeJob.Worker

**🟢 亮点**：`ClaimLoopAsync` 把轮询作为 liveness 下限、尊重 `freeSlots` 容量、`EmptyPollDelay` 退避、`IWorkerClaimTrigger` 脉冲合并；lease 续期、heartbeat、`FenceSession()` 在 heartbeat 被拒时正确触发新 Session 失败——实现与设计高度一致。

**🟡 风险（非阻断）**
- `CloseOutstandingAttemptsAsync`（`WorkerRuntimeService.cs:855` 附近）`catch` 仅 `LogWarning` 吞掉——优雅关闭时若本地收尾失败，可能留下孤儿 Attempt，依赖 reaper 兜底；建议至少记录 AttemptId 并考虑是否需 fail-fast。
- **超时是协作式**：`TimeoutExecutionMiddleware` + `CancellationTokenSource(TimeoutSeconds)` 只能取消协作型 handler；真正 runaway 的 async（忽略 token）不会被硬中止。设计已知此限制（文档标注 15s 硬限），可接受，但建议在文档明确"handler 必须响应 CancellationToken"。
- `CompleteAttemptAsync` 位于 `finally` 内且无 `try`（`WorkerRuntimeService.cs:560-586` 附近），对 BrokerDispatch 路径而言若 complete 失败可能导致 **double-ACK**（本地已 ACK 但 complete 抛错）。建议对其加 `try/catch` 与幂等保护。
- `catch (Exception ex)` 内 `if (stoppingToken.IsCancellationRequested) return;`（`WorkerRuntimeService.cs:605` 附近）吞掉一个本可观测的取消异常，建议 `return` 前记一条 trace。

### 2.4 KubeJob.Transport.RabbitMQ + KubeJob.Server

**🟡 风险**
- **Transport 消费端 ACK 语义需逐源核对**：设计声称"ingress 仅在 durable Run 被接受后 ACK 业务消息；dispatch 仅在 durable complete 后 ACK 执行信封"，但走查时未直接读到 transport 源码实现，未能 100% 确认 ACK 时机与 DLQ/TTL 重试队列的 `x-dead-letter-routing-key` 是否齐全。建议补一组集成测试断言"未持久化即 NACK 重投 / complete 前不 ACK"。
- vhost 权限引导假设（需管理员权限创建 exchange/queue）在多租户托管环境可能失败——建议文档说明并支持 `SkipDeclare`。
- **Server**：`JobRuntimeController`（Worker 控制端点）对入参/`WorkerId`/`SessionId` 缺少 null/字段校验，异常会冒泡成 500。建议统一模型校验。
- Dashboard：只读默认、mutating 动作有 `[ValidateAntiForgeryToken]` + cshtml 反 CSRF token、不渲染 payload/lease/fencing——**符合安全设计**。仅需注意 `AllowMutatingActions` 默认关闭，开启后务必配套 authz 策略。

### 2.5 KubeJob.Client + KubeJob.Generators + Tests

**🟢 亮点**：`JobKeyGenerator` 是**高质量增量生成器**——`ForAttributeWithMetadataName` 增量友好、重复属性名检测会报 `KJGEN002` **编译错误**（而非静默丢弃，见第 4 节）、`StableHint` 用 FNV-1a 稳定命名 hint、`#nullable enable`、全局命名空间安全。

**🟡 风险**
- `HttpJobClient` 成功判定（`/runs/{id}` 返回即视为成功）对 404 走"不存在则创建"分支，若服务端返回非预期 4xx 可能误判——建议显式区分 2xx/4xx/5xx。
- `HttpJobClient` 文档与实际建议的"双 transport 执行配置"有歧义：建议二选一（Client 用 HTTP 提交 + Worker 用 gRPC 拉取，或统一 HTTP）。
- 测试覆盖缺口：
  - `tests/` 中 ControlPlane 测试多走 `InMemoryJobRuntimeStore`，**未覆盖真实 PostgreSQL SQL**（Bug A/B 正是 SQL 路径，单测未捕获）。
  - BrokerDispatch 端到端路径（`RabbitMqExecutionDispatchIntegrationTests`，ADR 014 提及）在 src 中未见对应实现，建议确认是否已落地并纳入 CI。
  - `GeneratorNegative` 测试仅"应当报错"但**缺少自动化断言**（subagent 报告用 `#error` 注释占位），建议加 `[Fact]` 校验诊断产出。

## 4. 核对纪要与已修正的"假阳性"

为保证报告可信，对子代理给出的每条 🔴 我均逐行核对源码。以下 5 条初判为缺陷、核对后**修正**（不计入缺陷）：

1. **RetryPolicy `Linear` off-by-one**：核对 `RetryPolicy.cs:62-67`，`BaseDelay * attemptCount` 是设计定义，与 Exponential 基线不同，非 bug。
2. **Worker `ClaimLoop` drain 分支未 `return`**：`WorkerRuntimeService.cs:414-418` 用 `continue` 在 `while(!stoppingToken.IsCancellationRequested)` 内，host 关闭令牌取消即退出，正确。
3. **Worker 续期失败仅 `LogWarning` 不 fence**：`WorkerRuntimeService.cs:697-700` 是**设计如此**——fence 触发点是 heartbeat 被拒（`FenceSession()`），续期失败靠 lease 过期兜底（:858 注释）。非 bug。
4. **生成器嵌套类型 key 静默丢弃**：`JobKeyGenerator.cs:91-106` 对重复属性名**报 `KJGEN002` 编译错误**并仅丢弃重复项，非静默丢 key。
5. **Tombstone TTL 不计入重试退避 → 允许重复 Run**：`JobControlPlane.cs:63` 的 TTL 仅用于**可选**的 tombstone 去重优化（in-memory 实现甚至被 `<Compile Remove>`），**权威去重是 `UQ_Kj2_JobRuns_Idempotency` 唯一约束**。早过期只削弱优化、不破坏正确性。降级为 🟡（优化层面）。

## 6. 总体评价

- **设计**：A-（成熟度极高，仅 fail-open 与安全默认、能力映射文档两处需强化）。
- **代码**：B+（核心并发/协议扎实；PostgreSQL 存储层有 2 个 P0 缺陷需立即修；测试对真实存储与 BrokerDispatch 覆盖不足）。
- **最该立刻做**：修 P0 两个 PostgreSQL 缺陷 → 把安全默认改为 fail-closed → 补 PostgreSQL 集成测试与 BrokerDispatch E2E。
